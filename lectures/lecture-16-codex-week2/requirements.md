# 강의 요구사항 정의서: 2강

## 기본 정보

| 항목 | 내용 |
|------|------|
| 강의명 | 에이전트와 함께하는 삶의 전환: 2강 |
| 주제 | 에이전트는 무엇이고, 더 똑똑하게 쓰는 방법은 무엇인가 |
| 대상 | 비전공자 (30대~60대), 1강 수강자 |
| 형식 | 120분, 온라인 |
| 실습 도구 | ChatGPT 데스크탑 앱의 **Codex** |
| 산출물 | `week2.html` (발표용), `lecture.md` / `lecture.html` (Marp) |

## 1강과의 관계

| | 1강 | 2강 |
|---|-----|-----|
| 질문 | **왜** 배워야 하는가 | **무엇**이고 **어떻게** 쓰는가 |
| 내용 | 사례·동기, 챗봇과 에이전트 구분, 첫 실행 | 동작 원리, 아직 모르는 잠재력, 세 가지 사용법 |
| 끝난 상태 | 결과물 파일 하나를 만들어봄 | 자기에게 맞는 사용 방식을 하나 고름 |

1강은 "된다"를 보여줬습니다. 2강은 **왜 되는지, 그리고 왜 가끔 안 되는지**를 설명해서
수강생이 다음부터 혼자 판단할 수 있게 만듭니다.

## 2강 목표

1. LLM이 문장을 만드는 원리를 안다: 다음에 올 말을 확률로 고른다
2. 만든 사람도 모델의 잠재력을 다 모른다는 것과, 왜 모르는지를 안다
3. 잘 쓰는 방법에 정답표가 없고 **경험적으로 발견되어 공유되는 중**이라는 걸 안다
4. 세 가지 사용법을 구분한다: 프롬프트 엔지니어링 · 협력적 프롬프팅 · 메타프롬프트
5. 같은 과제를 세 방식으로 직접 시켜보고 **자기에게 맞는 방식을 하나 고른다**
6. 남의 방법을 찾아보는 것은 자기 경험 **다음**이라는 순서를 납득한다

## 핵심 메시지

> 지금까지 찾아낸 좋은 방법이 있을 뿐입니다.
> 내 결과물로 먼저 해보고, 그다음 남의 방법을 찾아보세요.

## 다뤄야 하는 개념

### 1. 다음 단어 예측기

- 문장 전체를 미리 계획하고 쓰는 것이 아니라, 다음에 올 말을 확률로 고르고 이어 붙임
- 같은 질문에 답이 매번 조금씩 다른 이유가 여기 있음
- **왜 중요한가**: 앞에 놓인 말(컨텍스트)이 다음 말의 확률을 바꿈. 프롬프트가 효과 있는 이유

### 2. 만든 사람도 잠재력을 다 모른다

이유 세 가지로 설명합니다.

| 이유 | 설명 |
|------|------|
| 가르친 게 아니라 생겼다 | "이 일을 하라"고 학습시킨 것이 아니라 방대한 글에서 다음 단어를 맞히게 했고, 그 과정에서 생긴 능력은 **시켜봐야** 확인됨 |
| 꺼내는 말을 찾아야 나온다 | 능력이 있어도 적절한 프롬프트를 못 찾으면 나오지 않음. 같은 모델이 프롬프트에 따라 전혀 다른 결과를 냄 |
| 조합을 전수 조사할 수 없다 | 시킬 수 있는 일의 조합이 사실상 무한해서, 출시 뒤에도 새 사용법이 계속 발견됨 |

근거 사례: 2022년에 "단계적으로 생각해봐"에 해당하는 프롬프트 한 줄로 수학 정답률이
크게 오르는 현상이 보고됨. 모델을 만든 뒤에 **발견된** 사용법입니다.

- [Chain-of-Thought Prompting Elicits Reasoning in Large Language Models](https://arxiv.org/abs/2201.11903) (2022-01)
- [Emergent Abilities of Large Language Models](https://arxiv.org/abs/2206.07682) (2022-06)

### 3. 정답표가 없다

- 지금 쓰이는 방법은 대부분 **사용자가 해보고 찾아내 공유한 것**
- 그래서 "지금까지 찾아낸 좋은 방법"이 있을 뿐, 더 좋은 방법이 없다는 보장은 없음
- 외우는 공부가 아니라 **해보고 기록하는 공부**

### 4. 세 가지 사용법

| | 방식 | 한 줄 |
|---|------|-------|
| ① | 프롬프트 엔지니어링 | 내가 목적·조건·형식·검증 방법을 적어줌 |
| ② | 협력적 프롬프팅 | 짧게 던지고, 되묻게 만들어 질문에 답하면서 채움 |
| ③ | 메타프롬프트 | 프롬프트를 써달라고 먼저 시킴 |

- 우열이 아니라 상황과 사람에 따라 다름
- 방법이 워낙 다양하므로 **일단 자기에게 익숙한 방식을 찾는 것**이 먼저
- ③이 도구로까지 만들어진 예: [Anthropic Console 프롬프트 생성기](https://www.anthropic.com/news/prompt-generator) (2024-05)

### 5. 내 방식을 찾아가는 순서

1. 내 업무, 내가 원하는 결과물로 세 방식을 **직접** 해봄
2. 같은 결과물을 남들은 어떻게 얻었는지 찾아봄
3. 더 좋은 방법이 있으면 내 방식에 넣음

순서가 중요합니다. 남의 방법을 먼저 보면 그게 내게 맞는지 판단할 기준이 없습니다.

## 설계 원칙

1강과 같습니다.

- 한 장에 **그림 하나 + 문장 하나**. 글을 많이 넣지 않음
- **비유를 쓰지 않음.** 표준 용어(LLM·컨텍스트·프롬프트·도구)를 쓰고 기능 설명을 덧붙임
- 목록은 **명사형으로 끝냄**
- 기술 설명은 슬라이드가 아니라 강사가 말로 함
- 모든 사실에 출처 링크 또는 발표자 노트의 근거
- 터미널을 다루지 않음. GUI 앱만 씀

## 실습 설계

**과제 선택**: 각자 자기 업무에서 "결과물이 눈에 보이는" 일 하나. 강사가 세 개쯤 예시를 띄웁니다.

| 단계 | 시간 | 하는 일 |
|------|------|---------|
| ① 프롬프트 엔지니어링 | 8분 | 목적·조건·형식·검증을 다 적어서 한 번에 시킴 |
| ② 협력적 프롬프팅 | 8분 | 한두 줄로 던지고, 질문을 받아 답하면서 진행 |
| ③ 메타프롬프트 | 8분 | 프롬프트를 써달라고 시킨 뒤, 받은 것을 그대로 실행 |
| 비교 기록 | 6분 | 세 결과를 표에 적음: 가까움 · 내 시간 · 재사용 |

한 번에 안 되는 게 정상이라는 걸 1강에서 가르쳤습니다. 2강에서는 **세 번 중 어느 것이
내게 맞았는지**만 고르면 됩니다.

## 성공 기준

- 수강생 전원이 같은 과제를 **세 방식으로** 시켜본 기록을 남김
- 각자 "나는 ②가 맞다" 같은 **한 문장**을 말할 수 있음
- "에이전트가 왜 가끔 틀리는지" 질문에 컨텍스트로 답할 수 있음
