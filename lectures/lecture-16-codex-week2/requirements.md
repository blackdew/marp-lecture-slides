# 강의 요구사항 정의서: 2주차

## 기본 정보

| 항목 | 내용 |
|------|------|
| 강의명 | 에이전트와 함께하는 삶의 전환: 2주차 |
| 주제 | 에이전트 잘 쓰는 방법 |
| 대상 | 비전공자 (30대~60대), 1주차 수강자 |
| 수강 환경 | 대부분 Windows |
| 형식 | 120분, 온라인. 이론 12분, 실습 89분 |
| 실습 도구 | ChatGPT 데스크탑 앱의 **Codex** |
| 실습 자료 | 수강생용 실습지(`worksheet.html`), 강사용 진행표(`runsheet.html`) |

수강 대상의 전제는 [1주차 요구사항](../lecture-15-codex-4weeks/requirements.md)과 같습니다.
터미널, 명령어, 복사·붙여넣기 숙련도, 영어를 전제하지 않습니다.

## 1주차와의 관계

| 구분 | 1주차 | 2주차 |
|------|-------|-------|
| 질문 | 왜 배워야 하는가 | 무엇까지 맡길 수 있는가 |
| 내용 | 사례, 동기, 첫 실행 | 작동 원리, 쓸모 있는 결과물을 만드는 실습 |
| 종료 시점의 상태 | 결과물 파일 한 개 제작 | 연하장, 보고서, 글, 음성을 직접 제작 |

## 학습 목표

1. 에이전트의 구조 설명: LLM, 도구 사용, 반복
2. LLM이 다음 낱말을 예측한다는 원리 설명
3. 요청에 내 상황을 적으면 결과가 달라진다는 사실 확인
4. 에이전트가 다른 앱을 조작해서 결과물을 만드는 과정 경험
5. 그림, 웹페이지, 보고서, 글, 음성을 요청해서 받는 경험
6. 만든 웹페이지를 인터넷 주소로 올려 다른 사람과 주고받는 경험
7. 결과에서 고칠 곳을 말로 요청하는 방법 적용

## 핵심 문장

> 오늘, 에이전트에게 맡길 수 있는 일의 범위를 넓히셨습니다.

## 용어

한 대상에 한 용어만 씁니다.

| 용어 | 뜻 | 쓰지 않는 표현 |
|------|-----|----------------|
| LLM | 대규모 언어 모델. 다음 낱말을 예측하는 모델 | 예측기, 두뇌 |
| 낱말 | LLM이 한 번에 고르는 단위 | 말, 조각, 토큰 |
| 내 상황 | 사용자만 아는 목적, 읽는 사람, 원하는 형식 | 맥락, 전제, 사정 |
| 요청 | 에이전트에게 보내는 문장 | 주문, 명령 |
| 허용 창 | 에이전트가 다른 앱을 쓰기 전에 묻는 창 | 권한 팝업 |
| 인터넷 주소 | 만든 웹페이지를 다른 사람이 열 수 있는 주소 | URL, 링크 |
| 예약 | 같은 요청을 정한 시각마다 실행하게 하는 설정 | 자동화, 스케줄 |

"LLM은 다음 낱말 예측만 훈련했다"는 말은 하지 않습니다. 기본 훈련 뒤에 지시를 따르도록 하는 추가 훈련이 있습니다. "기본 훈련은 다음 낱말 예측"이라고 말합니다.

"LLM은 문장을 미리 계획하지 않는다"는 말은 하지 않습니다. 모델이 뒤에 올 낱말을 미리 정해 둔다는 연구가 있습니다([Anthropic, 2025](https://www.anthropic.com/research/tracing-thoughts-language-model)). "한 번에 한 낱말씩 내놓는다"까지만 말합니다.

## 설계 원칙

형식은 1주차 덱(`../lecture-15-codex-4weeks/_build/w1.py`)을 그대로 따릅니다.

- 한 장에 **상징적인 그림 하나 + 문장 하나**. 글을 많이 넣지 않음
- 실습마다 결과 화면(`shot`)을 먼저 보여 주고, 다음 장에 요청 문장(`slide` + `lines`)을 표시
- 실습 예시는 수강생에게 실제로 쓸모 있는 결과물로 구성
- 화면의 요청 문장은 Codex에 실제로 보낸 문장만 사용. 확인한 범위는 발표자 노트의 "리허설"에 기록
- 요청 문장에는 내 상황을 적는 줄을 한두 줄씩 포함. 수강생은 이 줄을 자기 상황으로 바꿔 입력
- 실습마다 꼭 하는 단계와 시간이 남으면 하는 단계를 구분
- 기술 설명은 화면이 아니라 발표자 노트에 작성
- 비유 금지. 표준 기술 용어와 표준 교육 용어 사용
- 터미널 미사용. GUI 앱만 사용
- 만든 페이지가 공개되므로 전화번호, 주소, 주민등록번호는 적지 않도록 안내

빌드 후에는 화면 글자 수 중앙값과 그림이 있는 장표의 비율을 1주차와 비교합니다.

| 측정 항목 | 1주차 | 2주차 |
|-----------|-------|-------|
| 장표 수 | 56장 | 35장 |
| 화면 글자 수 (중앙값) | 34.5자 | 35자 |
| 그림이나 캡처가 있는 장표 | 64% | 54% |
| 아랫줄이 있는 장표 | 14% | 37% |

2주차는 요청 문장을 보여 주는 장표가 11장이어서 그림의 비율이 낮고 아랫줄의 비율이 높습니다.

## 실습 설계

실습마다 에이전트가 처음 쓰는 기능이 하나 이상 들어 있습니다.

| 실습 | 꼭 하는 단계 | 시간이 남으면 | 에이전트가 쓰는 기능 |
|------|--------------|---------------|----------------------|
| 1 연하장 | 그림판으로 그리기, 연하장 페이지와 주소, 서로 보내기 | 그림을 다른 느낌으로 한 장 더 | 다른 앱 조작, 그림 생성, 웹페이지 공개 |
| 2 계획 보고서 | 보고서 한 개 | 고칠 곳 말하기 | 여러 쪽짜리 문서 구성 |
| 3 관심 주제 보고서 | 보고서 한 개 | 매일 예약, 내용 확인, 지우기 | 웹 검색, 예약 실행 |
| 4 블로그 글 | 글 한 편 | 실제 장면을 덧붙여 다시 요청 | 글쓰기 |
| 5 쇼츠 | 인사말 음성 | 그림과 음성을 합친 영상 | 음성 생성, 영상 제작 |

- 연하장 실습은 채팅 하나에서 이어서 진행. 뒤 단계의 요청이 앞 단계에서 만든 그림을 가리킴
- 실습 2~4는 새 채팅에서 시작. 실습 5는 연하장을 만든 채팅으로 돌아가서 진행
- 화면에 나눠 적은 요청의 전체 문장은 `_build/w2.py`의 `SAY`에 있고, 실습지와 진행표가 이 문장을 사용

### 리허설 결과 (2026-11-27)

리허설은 Mac에서 두 가지 방식으로 했습니다. "앱"은 ChatGPT 데스크탑 앱의 Codex 화면이고, "실행 파일"은 앱에 들어 있는 Codex 실행 파일입니다.

| 요청 | 방식 | 걸린 시간 | 결과 |
|------|------|-----------|------|
| Freeform 앱을 열어서 눈사람 그리기 | 앱 | 허용 뒤 2분 39초 | 눈사람 그림을 PNG와 PDF로 저장. 허용 창 1회 |
| 그림 생성 | 앱 | 34초 | 그림이 채팅 안에 표시 |
| 연하장 페이지와 주소 (생성한 그림 한 장) | 앱 | 13초 + 3분 31초 | chatgpt.site 주소로 공개. "누구나 볼 수 있음" 표시 |
| 연하장 페이지와 주소 (화면의 문장, 그림 두 장) | 실행 파일 | 22초 + 1분 41초 | 연하장 제작. 주소는 발급되지 않음 |
| 여행 계획 보고서 | 실행 파일 | 30초 + 3분 42초 | 일정, 숙소, 예산, 준비물, 출처 |
| 공부 계획 보고서 | 실행 파일 | 23초 + 3분 55초 | 보고서 제작 |
| 사업 계획 보고서 | 실행 파일 | 27초 + 3분 12초 | 보고서 제작 |
| 관심 주제 보고서 | 실행 파일 | 33초 + 2분 41초 | 최근 소식 6개와 공식 출처 |
| 매일 예약 | 앱 | 30초 | "매일 아침 AI 에이전트 뉴스, 매일 오전 8:00" 예약 생성 |
| 예약 지우기 | 앱 | 14초 | 예약 삭제 |
| 블로그 글 | 실행 파일 | 21초 | 제목, 본문, 사진 자리 세 곳. 채팅에만 출력 |
| 인사말 음성 | 앱 | 1분 4초 | 20.6초 길이의 한국어 합성 음성 |
| 쇼츠 영상 | 앱 | 12초 + 57초 | 1080×1920, 20.6초, 자막 포함 |

걸린 시간이 둘로 적힌 요청은 에이전트가 구성을 먼저 보여 주고 확인을 구해서 "응, 만들어줘."를 한 번 더 보낸 경우입니다.

- 리허설한 계정에는 계획을 먼저 확인받으라는 전역 지침이 있습니다. 수강생의 Codex는 확인 없이 바로 만들 수 있고, 걸리는 시간도 다를 수 있습니다.
- 실행 파일 방식에서는 음성 만들기가 보안 제한에 막혀 실패했고, 같은 요청이 앱에서는 성공했습니다. 수업의 근거는 앱에서 나온 결과로 삼습니다.
- 예약을 만들 때 에이전트가 쓴 작업 지시문에는 보고서를 인터넷에 공개하라는 내용이 들어 있었습니다.
- 결과 화면은 `captures/`에 있습니다.

### 확인하지 못한 것

강의 전에 수강생과 같은 Windows와 같은 요금제의 계정으로 확인합니다.

| 항목 | 상태 |
|------|------|
| Windows의 그림판 조작 | 미확인. 화면의 문장은 리허설 문장에서 앱 이름만 바꾼 것 |
| Windows의 음성 만들기와 영상 만들기 | 미확인. 리허설한 Mac에는 영상 도구가 설치돼 있었음 |
| 수강생 요금제에서의 앱 조작, 웹페이지 공개, 예약 | 미확인 |
| 화면의 문장으로 연하장의 주소까지 받기 | 앱에서 미확인. 앱에서는 그림 한 장으로 확인 |
| 연하장 주소를 복사하는 위치 | 미확인 |
| 예약이 다음 날 실제로 실행되는지 | 미확인 |
| 에이전트가 메일이나 메신저로 직접 보내기 | 미확인. 수업에서는 주소를 채팅창에 올리는 방식 사용 |
| 에이전트가 블로그에 직접 올리기 | 미확인. 수업에서는 글을 복사해 붙여 넣는 데까지 안내 |

## 실습 자료

두 자료는 `_build/handouts.py`가 덱에서 만든 생성물입니다. 요청 문장, 표, 시각은 덱에서 읽어 옵니다.

| 자료 | 대상 | 내용 |
|------|------|------|
| `worksheet.html` | 수강생 | 실습별 요청 문장, 내 상황을 적는 칸, 확인 항목, 이번 주 과제 |
| `runsheet.html` | 강사 | 강의 전 준비 목록, Windows에서 확인할 것, 시각별 진행표, 채팅창에 올릴 문장, 막힌 수강생에게 알려줄 문장 |

- 실습지의 칸에는 화면에서 바로 입력합니다. 입력한 내용은 그 기기의 브라우저 저장소(`localStorage`)에만 저장되고 다른 곳으로 전송되지 않습니다.
- 저장소를 쓸 수 없는 브라우저에서는 입력은 되지만 저장되지 않고, 화면에 그 사실을 알립니다.
- 실습지는 인쇄해서 손으로 적어도 됩니다. 인쇄할 때는 입력한 내용이 함께 찍힙니다.

## 성공 기준

- 수강생 전원이 연하장을 만들어 주소를 채팅창에 올림
- 수강생 전원이 보고서 한 개 이상 제작
- "요청한 내용과 다른 결과가 나오는 이유"를 묻는 질문에 "내 상황을 알려주지 않아서"로 답변
- 예약을 만든 수강생 전원이 수업이 끝나기 전에 예약 삭제
