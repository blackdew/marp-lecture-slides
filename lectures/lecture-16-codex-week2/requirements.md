# 강의 요구사항 정의서: 2주차

## 기본 정보

| 항목 | 내용 |
|------|------|
| 강의명 | 에이전트와 함께하는 삶의 전환: 2주차 |
| 주제 | 에이전트 잘 쓰는 방법 |
| 대상 | 비전공자 (30대~60대), 1주차 수강자 |
| 형식 | 120분, 온라인 |
| 실습 도구 | ChatGPT 데스크탑 앱의 **Codex** |
| 실습 자료 | 수강생용 실습지(`worksheet.html`), 강사용 진행표(`runsheet.html`). 실습 과제는 고마운 사람에게 보내는 인사 카드 |

수강 대상의 전제는 [1주차 요구사항](../lecture-15-codex-4weeks/requirements.md)과 같습니다.
터미널, 명령어, 복사·붙여넣기 숙련도, 영어를 전제하지 않습니다.

## 1주차와의 관계

| 구분 | 1주차 | 2주차 |
|------|-------|-------|
| 질문 | 왜 배워야 하는가 | 무엇이고 어떻게 쓰는가 |
| 내용 | 사례, 동기, 첫 실행 | 작동 원리, 세 가지 방식 |
| 종료 시점의 상태 | 결과물 파일 한 개 제작 | 자신에게 맞는 방식 한 가지 선택 |

1주차 끝에서 예고한 "맡기는 범위를 넓힌다"는 3주차로 옮겼습니다. 2주차 열기에서 한 문장으로 알립니다.

## 학습 목표

1. LLM이 다음 낱말을 예측한다는 원리 설명
2. 낱말 예측 훈련에서 능력이 생기는 이유 설명
3. 모델을 만든 사람도 능력의 범위를 다 알지 못하는 이유 설명
4. 세 가지 방식 구분: 프롬프트 엔지니어링, 협력적 프롬프팅, 메타프롬프트
5. 같은 결과물을 세 방식으로 요청하고 자신에게 맞는 방식 한 가지 선택
6. 다른 사람의 방법을 찾아보는 순서 이해: 직접 적용이 먼저, 조사는 그다음

## 핵심 문장

> 오늘, 내 방식 하나를 고르셨습니다.

## 용어

한 대상에 한 용어만 씁니다.

| 용어 | 뜻 | 쓰지 않는 표현 |
|------|-----|----------------|
| LLM | 대규모 언어 모델. 다음 낱말을 예측하는 모델 | 예측기, 두뇌 |
| 낱말 | LLM이 한 번에 고르는 단위 | 말, 조각, 토큰 |
| 내 상황 | 사용자만 아는 목적, 읽는 사람, 원하는 형식 | 맥락, 전제, 사정 |
| 형식 | 결과물의 파일 종류, 분량, 항목 구성 | 모양 |
| 프롬프트 | 에이전트에게 보내는 요청문 | 말, 주문 |
| 방식 | 오늘 배우는 세 가지와 수강생이 고르는 한 가지 | 사용법 |
| 방법 | 에이전트를 잘 쓰는 방법 전체. 다른 사람이 찾아낸 것 포함 | 사용법 |

화면에서는 세 가지 방식을 쉬운 말로 먼저 적고, 용어는 아랫줄에 적습니다.

| 화면의 표기 | 용어 |
|-------------|------|
| 내가 다 적어서 요청 | 프롬프트 엔지니어링 |
| 질문에 답하면서 채우기 | 협력적 프롬프팅 |
| 프롬프트를 써달라고 하기 | 메타프롬프트 |

"프롬프트 엔지니어링"은 넓게는 프롬프트를 설계하는 일 전체를 가리킵니다. 이 강의에서는 사용자가 직접 작성하는 방식이라는 좁은 뜻으로 씁니다. 발표자 노트에 이 구분을 적어 둡니다.

"협력적 프롬프팅"은 이 강의에서 정한 뜻으로 씁니다: 에이전트가 묻고 사용자가 답하면서 요청을 함께 완성하는 방식. 표준 문서에서 정한 정의는 확인하지 못했습니다.

## 사실 근거

| 주장 | 출처 |
|------|------|
| 프롬프트에 한 문장을 덧붙여 산수 문제 정답률이 17.7%에서 78.7%로 상승 | [Kojima 외 (2022)](https://arxiv.org/abs/2205.11916), MultiArith, text-davinci-002 |
| 프롬프트 엔지니어링의 정의 | [OpenAI 프롬프트 엔지니어링 안내](https://developers.openai.com/api/docs/guides/prompt-engineering) |
| 한 줄 요청과 다섯 문장 요청의 카드 비교 | 2026-11-26에 ChatGPT 데스크탑 앱의 Codex로 실제 실행. 원본 화면은 `captures/`에 보관 |
| 프롬프트 작성을 모델에 맡기는 방식의 제품화 | [Anthropic 프롬프트 생성기 (2024-05)](https://www.anthropic.com/news/prompt-generator) |

"LLM은 다음 낱말 예측만 훈련했다"는 말은 하지 않습니다. 기본 훈련 뒤에 지시를 따르도록 하는 추가 훈련이 있습니다. "기본 훈련은 다음 낱말 예측"이라고 말합니다.

"LLM은 문장을 미리 계획하지 않는다"는 말은 하지 않습니다. 모델이 뒤에 올 낱말을 미리 정해 둔다는 연구가 있습니다([Anthropic, 2025](https://www.anthropic.com/research/tracing-thoughts-language-model)). "한 번에 한 낱말씩 내놓는다"까지만 말합니다.

## 설계 원칙

형식은 1주차 덱(`../lecture-15-codex-4weeks/_build/w1.py`)을 그대로 따릅니다.

- 한 장에 **상징적인 그림 하나 + 문장 하나**. 글을 많이 넣지 않음
- 기본 장표는 `sym`, 구간 사이는 `quip`, 화면 조작은 `shot`, 근거는 수치와 출처 링크
- 제목은 명사형이 기본. 서술형은 사실 전달, 화면 조작 안내, 따옴표로 묶은 프롬프트, 핵심 문장에 사용
- 제목 아래 설명 문장은 꼭 필요한 장표에만 표시
- 1주차가 쓰지 않은 부품(`agenda`, `cards`, `steps`, `term`, `chat`, `stmt`) 미사용
- 과제마다 **그대로 따라 칠 수 있는 길이의 프롬프트**를 화면에 표시
- 기술 설명은 화면이 아니라 발표자 노트에 작성
- 비유 금지. 표준 기술 용어와 표준 교육 용어 사용
- 모든 사실에 출처 링크 또는 발표자 노트의 근거 표시
- 터미널 미사용. GUI 앱만 사용

빌드 후에는 화면 글자 수 중앙값, 그림이 있는 장표의 비율, 최소 글자 크기를 1주차와 비교합니다.

| 측정 항목 | 1주차 | 2주차 목표 |
|-----------|-------|------------|
| 화면 글자 수 (중앙값) | 34자 | 40자 이하 |
| 그림이나 캡처가 있는 장표 | 64% | 60% 이상 |

## 시간 배분 (120분)

| 시각 | 구간 | 시간 | 내용 |
|------|------|------|------|
| 00:00 | 열기 | 8분 | 오늘 2시간 안내, 체크인 |
| 00:08 | 에이전트는 무엇인가 | 25분 | 에이전트의 구조, 다음 낱말 예측, 능력의 범위 |
| 00:33 | 첫 번째 방식 | 20분 | 내가 다 적어서 요청: 설명과 자기 문장 적기 10분 + 실습 10분 |
| 00:53 | 두 번째 방식 | 15분 | 질문에 답하면서 채우기: 설명 3분 + 실습 10분 + 확인 2분 |
| 01:08 | 쉬는 시간 | 10분 | |
| 01:18 | 세 번째 방식 | 13분 | 프롬프트를 써달라고 하기: 설명 2분 + 실습 11분 |
| 01:31 | 비교 | 9분 | 편했던 방식 고르기, 방식별 잘 맞는 일, 확인 질문 |
| 01:40 | 내 방식 찾기 | 12분 | 내 일에 먼저 적용, 다른 사람의 방법 찾기: 실습 3분 포함 |
| 01:52 | 마무리 | 8분 | 이번 주에 할 일 3분 + 질문 5분 |

설명과 실습을 번갈아 둡니다. 실습 직전인 00:42에 두 요청의 결과를 나란히 보여주고, 첫 실습은 00:43에 시작합니다. 직접 해보는 시간은 모두 34분입니다.

## 실습 설계

**과제**: 고마운 사람에게 보내는 인사 카드를 웹페이지로 만듭니다. 세 가지 방식으로 세 장을 만들고, 받는 사람은 실습마다 바꿉니다. 마지막에는 다른 방법을 에이전트에게 묻습니다. 예시는 연말 인사로 들지만 과제 이름은 "인사 카드"로 두어 다른 시기에도 씁니다.

인사 카드를 과제로 정한 이유는 네 가지입니다.

- 에이전트가 파일을 만들고, 결과물이 화면에서 움직입니다. 채팅 답변으로 끝나지 않습니다.
- 받는 사람과 함께한 일은 수강생만 압니다. 그래서 "에이전트는 내 상황을 모른다"는 원리를 실습에서 직접 확인합니다.
- 목적, 읽는 사람, 형식이 과제 안에 이미 들어 있습니다.
- 카드는 보낼 사람이 여러 명이어서, 세 번째 방식의 프롬프트를 받는 사람만 바꿔 다시 씁니다.

안내문처럼 채팅 답변으로 끝나는 문서는 과제로 쓰지 않습니다. 한 줄로 요청해도 쓸 만한 결과가 나와서, 내 상황을 알려줄 이유가 드러나지 않습니다.

| 회차 | 방식 | 화면의 프롬프트 | 시간 |
|------|------|-----------------|------|
| 실습 1 | 내 상황(목적, 읽는 사람, 형식)과 확인 방법을 적어서 요청 | 다섯 문장 예시 | 8분 + 수정 요청 2분 |
| 실습 2 | 짧게 요청하고 에이전트의 질문에 답변 | "인사 카드를 새 파일로 만들래. 폴더의 파일은 읽지 말고, 나한테 질문부터 해줘" | 10분 |
| 실습 3 | 프롬프트 작성 요청, 고쳐서 실행, 파일로 저장 | "인사 카드를 새 파일로 만들래. 폴더의 파일은 읽지 말고, 프롬프트만 먼저 써줘" | 4분 + 5분 + 2분 |
| 실습 4 | 같은 카드를 요청하는 다른 방법 질문 | "이 카드를 너한테 요청하는 다른 방법 세 가지를 알려줘" | 3분 |

- 바탕화면에 빈 `2주차` 폴더를 만들고 그 폴더에서만 작업합니다.
- 회차마다 새 채팅에서 시작합니다. 앞 회차의 대화를 에이전트가 읽지 않게 하기 위해서입니다.
- 폴더에는 앞 회차의 결과 파일이 남습니다. 그래서 실습 2와 실습 3의 프롬프트에 "새 파일로"와 "폴더의 파일은 읽지 말고"를 넣습니다. 앞의 말은 덮어쓰기를, 뒤의 말은 앞 결과물 참조를 막습니다.
- 한 줄씩 늘어나는 다섯 장에서 수강생이 첫 번째 카드에 맞는 문장을 실습지에 적습니다. 실습 1에서는 적어 둔 문장을 입력합니다.
- 엔터를 누르면 전송됩니다. 여러 문장은 줄을 바꾸지 않고 이어서 적은 뒤 한 번에 보냅니다. 이 안내는 실습 1 화면에 표시합니다.
- 결과 비교 예시를 만든 컴퓨터에는 계획을 먼저 확인받으라는 전역 지침이 있었습니다. 수강생의 환경에서는 진행 방식과 걸리는 시간이 다를 수 있으므로, 노트에 그 사실을 적었습니다.
- 카드를 보낼 때는 사진 파일로 저장해 달라고 요청하거나 화면을 캡처합니다. 웹페이지 파일은 메신저에서 바로 열기 어렵습니다.
- 결과물의 파일 종류는 웹페이지로 정합니다. 1주차 실습에서 만들어 본 종류이고, 움직이는 효과를 넣을 수 있습니다.
- 프롬프트 저장은 복사와 붙여넣기를 쓰지 않고 에이전트에게 파일로 저장해 달라고 요청합니다.
- 화면의 프롬프트는 그대로 따라 치면 실행되는 완결된 문장으로 적습니다. 꼭 필요한 조건을 아랫줄로 빼지 않습니다.
- 뒤 회차일수록 과제를 더 잘 알게 됩니다. 그래서 결과의 품질이 아니라 어느 방식이 편했는지를 기준으로 고릅니다.
- 실습 1에는 결과를 받은 뒤 수정을 한 번 요청하는 단계가 있습니다. 1주차에서 연습한 방법을 이어 갑니다.
- 전화번호, 주소, 주민등록번호는 적지 않고, 화면에 보여도 괜찮은 이야기만 적게 합니다. 이 안내는 받는 사람을 정하는 장표의 화면에 표시합니다.

## 실습 자료

두 자료는 `_build/handouts.py`가 덱에서 만든 생성물입니다. 프롬프트 문장, 표, 시각은 덱에서 읽어 옵니다.

| 자료 | 대상 | 내용 |
|------|------|------|
| `worksheet.html` | 수강생 | 다섯 문장을 적는 칸, 실습 1~4에서 따라 칠 프롬프트, 편했던 정도 기록란, 이번 주 과제 기록란 |
| `runsheet.html` | 강사 | 강의 전 준비 목록, 시각별 진행표, 채팅창에 올릴 문장, 막힌 수강생에게 알려줄 문장 |

- 실습지에는 카드를 받을 세 사람을 적는 칸과 지어낸 예시 세 가지가 들어 있습니다.
- 실습지는 인쇄하거나 휴대폰으로 볼 수 있습니다. 강사가 받는 사람을 정하는 장표에서 주소를 채팅창에 올립니다.
- 강의 상세 페이지에 실습지로 가는 버튼이 표시됩니다. 진행표는 링크하지 않습니다.

## 성공 기준

- 수강생 전원이 `2주차` 폴더에 인사 카드 세 장 제작
- 각자 "나는 ○번째 방식이 편했다"는 한 문장 발표
- "요청한 내용과 다른 결과가 나오는 이유"를 묻는 확인 질문에 "내 상황을 알려주지 않아서"로 답변
